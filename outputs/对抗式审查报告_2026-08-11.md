## 二、P0 详述

### 发现 1：git 历史 PII 未处理（旧 R8，从未行动）

**证据**：`git log --all -S '张明远'` 命中 3 个 commit，其中 `742c200`（v1.0 初始提交）是引入点。报告当前版本已模糊化（d44cbd9），但历史 commit 里原始姓名、注册号、电话、地址完整可读。仓库为 public。

**为什么是 P0**：模糊化做的是"当前版本"，安全做的是"全部历史"。公开仓库 + 完整历史 = 模糊化效果被 `git log -p` 一条命令清零。

**三个选项**（需 sun 决策）：
- **A. 确认数据虚构** → 无需动作，在 README 标注"所有人物/证件均为虚构测试数据"。**成本最低，如果数据确实是编的，这是正解。**
- **B. 重写历史** → `git filter-repo` 清除 `742c200` 中的报告文件后 force push。代价：所有 commit hash 变化，克隆者需重新 clone。
- **C. 仓库转 private** → 一劳永逸，但失去公开分享价值。

### 发现 2：交接文档二次泄露（本次已修复）

**证据**：commit `22d1ca6` 的 HANDOFF-2026-08-08.md §1.2.1 "模糊化清单"表格中，以"原文 → 模糊化"格式完整写出了 5 个原始人名、2 个电话、注册号、地址——等于模糊化完成后的下一个 commit 把原文又公开发布了一遍。

**已修复**：本次审查已将该表格改为只描述处理方式（"全部替换为姓+某某格式"），不留存原文。但 **commit 22d1ca6 的历史记录中仍有原文**，与发现 1 一并处理。

### 发现 4：Excel 模板打开即报错

**证据**：gen 脚本把文本占位符写进输入单元格（实测 B6=`'如: 25000'`(str)、B7-B12=`'1.00'`(str)），用 formulas 库实际计算比较法模板：**82 格成功，12 格错误**（#VALUE!/#DIV/0!），错误集中在所有依赖输入的公式上。

**用户影响**：这是用户打开模板的第一眼——满屏红色错误。对一个"估价师出身、非程序员"的目标用户，第一印象是"这个表是坏的"。

**修复方向**（二选一）：
- 占位符改为**真实示例数值**（如成交价 25000、修正系数 1.00 直接写数字），"如: xxx"说明移入批注——推荐，模板即可用
- 输入单元格留空，错误提示靠数据验证——打开时公式仍显示 #DIV/0!，观感差

### 发现 5：Schema 对抗测试 8 攻 7 破

**方法**：基于合法 example 构造 8 种恶意变异，用 validate_full/validate_fragment 实测。

| 攻击 | 构造 | 结果 |
|------|------|:--:|
| 1 | `methods: {}`（一份没有任何测算方法的"估价结果"） | 🚨 通过 |
| 2 | `weightSum: 999`（SKILL.md 明文要求必须=1.0） | 🚨 通过 |
| 3 | `valueDate: "下周三"` | 🚨 通过 |
| 4 | `redLineChecks: []`（一条红线都没检查） | 🚨 通过 |
| 5 | `project.cllent`（拼错的字段名） | 🚨 通过 |
| 6 | `applicable: false` 且缺 finalValue | ✅ 拦截 |
| 7 | `methods.fakeMethod`（未定义的方法名） | 🚨 通过 |
| 8 | 可比实例仅 1 个（红线要求≥3） | 🚨 通过 |

**根因分析**：
- 攻击 1/7：`methods` 对象没有 `additionalProperties: false` 和任何约束
- 攻击 2：schema 只要求 weightSum "存在"，没有 `const: 1.0` 或 maximum/minimum
- 攻击 3：`format: "date"` 默认不校验（jsonschema 需显式启用 FormatChecker，见发现 10）
- 攻击 4/8：数组没有 `minItems`
- 攻击 5：project/property/valuation/result 等嵌套对象全部没有 `additionalProperties: false`（只在根和 4 个方法对象上加了）

**测试为何没抓到**：50 个用例里，负面用例（TestNegativeCases）只测了"缺字段/多字段在根层和方法层"，业务规则用例（TestBusinessRules）只验证**已知良好样本**是否自洽——样本是手写的，永远自洽，永远绿。**没有一个用例是"构造违规数据，断言必须被拦截"**。这是典型的"测试通过 ≠ 验证有效"。

**修复**：schema 补齐 6 处约束 + 新增一批"恶意输入必须被拦截"的对抗测试（把本报告的攻击清单固化成测试）。

### 发现 6：validate_degraded 死文档

**证据**：`scripts/validate_appraisal_json.py` 第 87 行 docstring 写着"额外检查：不能有 redLineChecks 全为 passed=true 的方法（降级模式无法保证红线已验）"，但第 89-97 行实现里**只有 sourceMode 检查，红线检查根本不存在**。文档承诺了一个不存在的安全特性。

### 发现 7：install.sh 两个 bug

**证据**：
- `bash -c 'set -euo pipefail; found=0; ((found++)); echo survived'` → **直接退出，exit 1**（`found++` 后缀自增返回旧值 0，算术求值为 0 = 假 = 非零退出码，被 `set -e` 捕获）。install.sh 里因处于命令替换的子 shell 环境侥幸未崩，但行为依赖 bash 版本，是定时炸弹。应改 `found=$((found+1))`。
- 实测 `bash install.sh --check`：verify 函数的逐行明细（每个技能的行数）与汇总行混在一起输出，格式破碎不可读。
