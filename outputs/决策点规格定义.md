## 一、通用框架

### 1.1 决策点规格六要素

每个决策点规格由六要素组成，Phase 3 编排层按此实现：

| 要素 | 说明 |
|------|------|
| **标识** | id / name / phase / trigger / riskLevel / method |
| **触发条件** | 何时暂停（固定 DP 为 always；条件 DP 为 method 适用 + 步骤位置） |
| **暂停位置** | 工作流中的精确位置（哪个技能步骤之后、之前） |
| **输入条件** | 生成决策包所需的全部结构化数据（schema JSONPath 引用） |
| **内容模板** | 决策包五段式（结论/证据/理由/风险/对比）逐段生成规范 |
| **输出动作** | 人类决策三种动作（批准/调整/驳回）后 AI 的后续行为 |

### 1.2 决策包五段式模板（所有 DP 通用）

```
conclusion  ── 一句话给结论（结论先行，不堆砌信息）
evidence    ── 每条证据 = item（内容）+ source（信源）+ 可溯源
reasoning   ── 为什么得出此结论（引用 GB/T 50291-2015 条文 / 方法逻辑）
risks       ── 按错误代价分级（P0 不可逆 / P1 可修正 / P2 监控），每条含 mitigation
comparison  ── 仅方法特定 DP：与估价对象逐项差异（必须可从结构化数据溯源）
```

**证据溯源红线**：`evidence` 与 `comparison` 中的每个断言必须能从工程文件结构化字段验证（如面积差 = `property.area − comparableInstances[i].area`）。禁止编造结构化数据中不存在的信息（P1-4 教训：楼层差曾因无法溯源被对抗式审查揪出）。

**信源等级（sourceGrade）**：T0=官方/一手（不动产权证、政府公告、成交登记）；T1=平台/机构（链家、贝壳成交记录）；T2=口头/间接（中介实测、电话询价）。`evidence.source` 中的等级标注必须与结构化 `sourceGrade` 一致。

### 1.3 人类决策动作语义

| 动作 | 状态 | 语义 | 后续行为 |
|------|------|------|---------|
| 批准 | `approved` | 接受 AI 推荐内容 | 按 DP 定义的"批准后"动作继续执行 |
| 调整 | `modified` | 内容基本可用，估价师给出修改意见（必填 `modifications`） | 按修改意见落地后继续执行；**不产生新 DP** |
| 驳回 | `rejected` | 内容不可用，整体否决重做 | **创建新 DP**（见第四章 决策链模型） |

**边界约定**：调整（modified）用于"局部修正后即可定稿"；驳回（rejected）用于"AI 重新生成"。两者由估价师按问题严重度判断，AI 不代做决定。

## 二、固定决策点规格（每次估价都触发）

### DP1 估价事项确认 — P0

| 要素 | 内容 |
|------|------|
| **标识** | id=`DP1`，name=估价事项确认，phase=`preCalculation`，trigger=`always`，riskLevel=`P0` |
| **触发条件** | 用户目标输入完成后，资料搜集开始前（固定 DP，必触发） |
| **暂停位置** | 用户描述目标 → 校验四要素 → **暂停** → 资料搜集 |
| **输入条件** | `project.{name,purpose,client,agency,appraiser}`、`valuation.{valueDate,valueType}`、`property.{area,usage,address,propertyType}` |
| **内容模板** | |
| — conclusion | 「估价目的：{purpose}；价值时点：{valueDate}；估价对象：{address}（{usage}，{area} m²）；价值类型：{valueType}」 |
| — evidence | ① 估价目的 ← 委托合同/评估委托书 ② 估价对象四至与面积 ← 不动产权证 ③ 价值时点 ← 委托书约定 |

| — comparison | 无（固定 DP 省略字段） |
| **输出动作** | |
| — approved | 进入资料搜集 |
| — modified | 按 `modifications` 修正四要素后进入资料搜集（不产生新 DP） |
| — rejected | 要求估价师重述目标 → AI 重新生成 → 创建新 DP `DP1-2`（supersedes=`DP1`） |

### DP3 测算结果审核 — P1

| 要素 | 内容 |
|------|------|
| **标识** | id=`DP3`，name=测算结果审核，phase=`postMethod`，trigger=`always`，riskLevel=`P1` |
| **触发条件** | 全部采用的方法测算完成后，报告生成前（固定 DP，必触发） |
| **暂停位置** | 各方法测算 + 红线校验 → **暂停** → 报告生成 |
| **输入条件** | 各方法 `finalValue`、`redLineChecks`、`crossMethodConsistency`、`crossMethodDifference`、`calculationChain` |
| **内容模板** | |
| — conclusion | 「{方法A} {结果}，{方法B} {结果}，红线 {n}/{n} 通过，差异 {x}%，建议加权 {结果}」 |
| — evidence | ① 红线校验表（threshold/actualValue/passed）② 修正系数明细 ③ 跨方法一致性检查 ④ 差异比（最高/最低 ≤1.2 红线） |
| — reasoning | 7.0.15 条结果确定；差异 <10% 可接受、>10% 须解释；权重依据市场证据 |
| — risks | P1：某实例修正接近 20% 上限、两方法差异偏大未解释；P2：权重取整引入偏差 |
| — comparison | 无（结果层面） |
| **输出动作** | |
| — approved | 进入报告生成 |
| — modified | 按修改意见局部重算（换可比实例/调权重/调修正系数）后重提 DP3 内容（**在原 DP 上更新并标 modified**，不产生新 DP） |
| — rejected | 整体重新测算 → 创建新 DP `DP3-2`（supersedes=`DP3`） |

> **说明**：DP3 的 modified 与 rejected 边界——参数级修正（换实例、调权重）属 modified，AI 直接落地重算；若估价师认为测算逻辑或基础数据不可信，属 rejected，整体重算。

## 四、决策链与驳回后行为模型（P2-2 决策）

### 4.1 决策：驳回后创建新 DP，旧 DP 保留为不可变审计记录

`status=rejected` 后，**禁止修改或删除旧 DP**，AI 创建**新 DP**（新 ID）继续决策链。理由：

1. **审计合规**：GB/T 50291-2015 要求估价过程可追溯。估价师"否决了什么、为何否决"（`humanDecision.comment`）是审计关键证据——修改旧 DP 等于销毁证据。
2. **决策链回溯**：新 DP 沿 `supersedes` 链可回看完整迭代（初版建议 → 否决原因 → 修正版建议），报告审核时可还原全部决策过程。
3. **AI 学习信号**：`rejected` + `comment` 记录了估价师的专业判断，是 AI 改进决策包生成的训练样本。

### 4.2 决策链模型

```
decisionPoints: [
  { id: "DP-comp",   attempt: 1, status: "rejected", humanDecision: {action:"rejected", comment:"实例C信源等级低，换同小区实例"} },
  { id: "DP-comp-2", attempt: 2, supersedes: "DP-comp", status: "approved", ... }
]
```

**规则**（写入 schema + 业务校验）：
1. `supersedes`（可选 string）= 被本 DP 取代的前一个 DP 的 id；`attempt`（可选 int ≥1）= 决策链内第几次尝试（首个 DP 为 1 或省略）。
2. **只有 `status=rejected` 的 DP 才会被取代**（approved/modified 为终结状态）。
3. 决策链为 1:1 链表：同一 DP 只能被一个后继 DP 取代（防分叉）；沿链不得成环。
4. `attempt` 若提供必须 = 被取代 DP 的 `attempt + 1`。
5. 新 DP 内容必须**回应否决原因**：conclusion 更新、evidence 补充或更换、原风险项标注 mitigation 状态。

### 4.3 状态机

```
                ┌── approved（终结）
pending ────────┼── modified（终结，内容按估价师意见定稿）
                └── rejected（非终结）→ 生成新 DP（supersedes 指向它）→ pending
```

### 4.4 Schema 建模（v1.4）

`decisionPoint` 新增两个**可选**字段（向后兼容 v1.3）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| `supersedes` | string | 否 | 被本 DP 取代的前一个 DP 的 id（仅驳回后继 DP 使用） |
| `attempt` | integer | 否 | 决策链内尝试序号（≥1）。无 `supersedes` 时省略或 1 |

跨 DP 约束（数组级，JSON Schema 无法表达）在 `validate_appraisal_json.py` 业务校验 `_check_decision_chain()` 落地：

| # | 校验 | 违规示例 |
|---|------|---------|
| C1 | `supersedes` 引用的 id 必须存在 | `DP-comp-2` supersedes 一个不存在的 id |
| C2 | 不得自引用 | `DP-comp` supersedes 自身 |
| C3 | 被取代的 DP 必须 `status=rejected` | supersedes 一个 `approved` 的 DP |
| C4 | 1:1 后继（同一 id 最多被一个 DP 取代） | 两个 DP 都 supersedes `DP-comp` |
| C5 | 不得成环 | A→B→A |
| C6 | `attempt` 一致性（若提供，须 = 前驱 attempt+1） | 前驱 attempt=1 而新 DP attempt=3 |
