## 二、P0 — 必须修复

### P0-1：Round 2 修复引入浮点 attempt 双端漂移（回归，非原有缺陷）

**证据**（对抗探测，同一输入双端对照）：

| 输入 | 修复前双端 | 修复后双端 | 判定 |
|---|---|---|---|
| b.attempt=2.5 | PY 报 C6 / JS 报 C6（一致） | PY **静默通过** / JS 报 C6 | **漂移** |
| a.attempt=2.0, b.attempt=3 | 双端通过（一致） | PY 报 C6 / JS **静默通过** | **漂移** |
| a.attempt=2.0, b.attempt=2 | 双端报 C6（一致） | PY **静默通过** / JS 报 C6 | **漂移** |

**根因**：Round 2 把 Python C6 入口改为 `isinstance(attempt, int)`，把浮点排除出检查；而 JS 的 `typeof attempt === "number"` 仍包含浮点。一致性边界被修复动作本身移动了。修复前 `attempt is not None` 双端对浮点行为相同。

**真实暴露面**（不是理论问题）：
1. **schema 挡不住 2.0**：`attempt` schema 为 `type: integer`，jsonschema 4.26 对整数值浮点 2.0 **接受**（实测）→ 2.0 通过 schema 到达 C6，Python 静默通过。
2. **前端路径无 schema**：`dp-console.html` 直接调用 `DPCore.validateChain()`，浏览器里 attempt=2.5 报 C6；同一 JSON 用命令行 `validate_appraisal_json.py` 验证则通过 → **用户可见的双端结论不一致**，正是这轮迭代要消灭的问题本身。

**为什么回归测试没抓住**：生成器全部 16 个 kind 只用整数 attempt（含 `attempt_str` 却无 `attempt_float`）。"回归全绿"与"未引入回归"之间隔着测试集覆盖度。
