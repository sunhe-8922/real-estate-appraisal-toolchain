# 对抗式审查报告（第三轮）：编排层接入 + 前端决策包控制台

> 审查对象：Phase 3 编排层接入产物  
> 审查时间：2026-08-18  
> 审查范围：`app/js/dp-core.js`、`app/dp-console.html`、`skills/appraisal-orchestrator/SKILL.md`、前端产物 JSON（AI 生成的决策包 / 人类决策响应 / 决策链）

## 1. 审查策略

本轮对抗式审查聚焦"接入后的产物"与"规格约束"的贴合度：

1. **Schema 合规性**：前端交互生成的决策响应 JSON 是否满足 `schema/appraisal-result.schema.json` v1.4 + 业务校验 C1-C6。
2. **决策链模型 4.2**：`rejected` 后是否创建新 DP、旧 DP 是否保留、`supersedes`/`attempt` 是否正确。
3. **五段式与证据溯源**：决策包是否包含结论/证据/理由/风险/与估价对象差异，信源是否可溯源。
4. **风险颜色编码与交互**：P0 红/P1 橙/P2 灰、批准/调整/驳回三分支、调整必填 modifications、驳回必填 comment。
5. **离线零构建**：前端是否全部 vendor 本地化、无外部 CDN、可双击 `index.html` 运行。

## 2. 发现问题与修复

### P1 — 驳回按钮的后继预览为空

- **表现**：点击"驳回"后，操作面板打开，但"驳回后将创建 DP-comp-2"的预览未显示。
- **根因**：`dp-core.js::buildSuccessorShell()` 要求被取代的 DP 状态必须是 `rejected`，而预览时该 DP 仍为 `pending`。
- **修复**：`app/dp-console.html` 的 `open("rejected")` 中构造临时 `rejectedPreview = Object.assign({}, dp, { status: "rejected" })` 用于预览，不改变原 DP 状态。
- **验证**：预览现在正确显示后继 DP id / supersedes / attempt。

### P2 — 驳回后未自动创建新决策点

- **表现**：点击"驳回→确认"后，仅旧 DP 变为 `rejected`，未生成 `DP-comp-2`。
- **根因**：前端 `submit()` 只调用 `DPCore.applyDecision()` 写回旧 DP，未按决策链模型 4.2 追加后继 DP。
- **修复**：`submit()` 在 `action === "rejected"` 时调用 `DPCore.buildSuccessorShell()` 并将 `successor` push 到 `state.data.decisionPoints`。
- **验证**：驳回后正确生成 `status=pending` 的 `DP-comp-2`，`supersedes=DP-comp`，`attempt=2`。

### P3 — 测试 fixture 字段名不匹配 schema（非前端代码缺陷）

- **表现**：最初用最小测试数据 `test-pending.json` 导出验证时，报 `comparison` 字段应为 `instance/differences`、phase 应为 `preCalculation`、顶层 required 缺失等 28 项错误。
- **根因**：该 fixture 为临时构造的最小骨架，未完整遵循 schema，不代表前端 UI 输出问题。
- **处理**：换用完整合规的 `tests/fixtures/orchestrator_pending_comps.json`（基于 `example-武汉洪山住宅.json`）重新验证。
- **结论**：前端产物在输入合规的前提下输出合规。

### P4 — schema 对 evidence/risks 强制 minItems=1

- **表现**：schema v1.4 中 `decisionPoint.evidence` 与 `decisionPoint.risks` 均要求 `minItems: 1`。
- **影响**：即使 P0 固定决策点 DP1，也必须有至少一条证据和一条风险。示例数据已满足此约束。
- **结论**：编排层 AI 生成决策包时必须保证 evidence/risks 非空；该约束已在 schema 层面强制，前端只负责渲染与记录。

### P5 — Git Bash `$TEMP` 环境变量在 Python 子进程中不一致

- **表现**：尝试用 `$TEMP/xxx` 保存 agent-browser 输出时，Python 侧解析为 `/tmp/xxx` 导致文件未找到。
- **根因**：Git Bash 的 `$TEMP` 与 Python 启动时的 Windows 临时目录环境不一致。
- **处理**：改为直接写入项目目录 `tests/fixtures/` 下的临时文件。
- **结论**：过程问题，不影响产物。

## 4. 遗留风险与建议

### R1 — 前端仅生成"决策响应 JSON"，不自动回填完整工程

当前 `dp-console.html` 仅修改 `decisionPoints[]` 并导出 JSON。编排层 AI 需要读取该 JSON，将人类决策结果合并回主工程，并继续后续方法计算。建议在编排层 skill 中明确"合并决策响应 → 继续工作流"的步骤。

### R2 — 驳回后新 DP 五段式为占位内容

`buildSuccessorShell()` 生成的 successor 复制旧 DP 的 evidence/risks/comparison，但 `conclusion`/`reasoning` 为空字符串。这符合规格（4.2 规则 5：由编排层 AI 重写以回应否决原因），但前端导出的 JSON 中可能出现空 conclusion。schema 并未禁止空字符串，但建议编排层在继续前必须重写这两个字段，并在校验脚本中增加可选的业务警告（非错误）。

### R3 — 调整（modified）不产生新 DP，但前端未显式提示 AI 执行方式

规格 1.3 明确 `modified` = 局部修正，不产生新 DP。当前前端仅记录 modifications 文本，不自动触发 AI 重跑。建议在 UI 文案和操作成功提示中强化"AI 将按调整内容落地后继续"的说明。

### R4 — 决策链可视化未处理三节点以上长链

当前 `resolveChain()` 按 1:1 后继遍历，理论上支持任意长度链；但示例中只验证了 2 节点链。建议补充 3 节点链的前端 fixture 测试（DP-comp → DP-comp-2 → DP-comp-3）。

### R5 — `install.sh` 需用户重启 WorkBuddy 才能识别新 skill

已按项目约定在 install.sh 的 `EXPECTED_SKILLS` 与完成提示中补录 `appraisal-orchestrator`。skill 索引在 WorkBuddy 启动时一次性完成，需提醒用户重启。
