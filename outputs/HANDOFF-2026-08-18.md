## 一、本次完成的功能

### 1.1 Schema v1.3 — 人工决策点 `decisionPoints` 字段（提交 `1e6ecbe`）

在 v1.2 基础上新增**可选**字段，向后兼容（v1.2 数据迁移到 v1.3 仅更新版本号）：

| 新增 | 说明 |
|------|------|
| 顶层 `decisionPoints` | `array`（$ref: decisionPoint），人工决策点列表：AI 在关键专业判断节点暂停，呈现"决策包"等待估价师批准/调整/驳回 |
| `$defs.decisionPoint` | `required: [id, name, phase, trigger, riskLevel, status, conclusion, evidence, reasoning, risks]`，`additionalProperties: false` |
| `$defs.evidenceItem` | `required: [item, source]` |
| `$defs.riskItem` | `required: [description, level]`，可选 `mitigation` |
| `$defs.comparisonItem` | `required: [instance, differences]`（方法特定 DP 使用，如可比实例选取） |
| `humanDecision` | 人类决策记录：`action`（approved/modified/rejected）+ `decidedBy` + 可选 `timestamp/modifications/comment` |

**decisionPoint 关键属性**：
- `phase`: `preCalculation` / `inMethod` / `postMethod` / `postReport`
- `trigger`: `always`（固定决策点）或 `method:comps|income|cost|hypotheticalDev`（条件决策点）
- `riskLevel`: `P0`（错误代价不可逆，必须人工确认）/ `P1`（建议确认）/ `P2`（知会即可）
- `status`: `pending` / `approved` / `modified` / `rejected`
- `comparison`: 与估价对象差异数组（仅方法特定 DP 使用，固定 DP 应省略字段而非置 null）

**设计原则**：结论先行（每个决策点必须先给结论再展开证据）；风险分级（P0/P1/P2）；`decisionPoints` 为**运行时字段**，由 AI 在估价流程中动态生成，不通过迁移填充。

**决策点定义**（详见 `outputs/人工决策点架构设计.md`）：
- 固定 DP：DP1 估价事项确认(P0) / DP2 测算方案确认(P1) / DP3 测算结果审核(P1) / DP4 报告签发(P0)
- 条件 DP：DP-comp 可比实例选取(P1) / DP-income 报酬率确定(P1) / DP-cost 重置成本确定(P1) / DP-hypoth 开发完成后价值确定(P1)
- 典型估价序列：DP1 → DP2 → DP-comp → DP-income(可选) → DP3 → DP4（5-6 个决策点）

### 1.5 v1.3.1 对抗式审查修复（提交 `1e4783f`）

| 编号 | 修复内容 | 方式 |
|------|---------|------|
| P0-1 | 非 pending 状态必须有人类决策记录 | `if/then` required humanDecision |
| P0-2 | `action=modified` 必须填写非空 `modifications` | `if/then` + minLength: 1 |
| P0-3 | `trigger=method:xxx` 必须填写 `method` | `if/then` required method |
| P0-4 | `status=pending` 禁止有人类决策记录 | `else: not required` |
| P0-5 | `trigger` 限定枚举 `always|method:(comps\|income\|cost\|hypotheticalDev)` | pattern 约束 |
| P0-6 | `status` 与 `humanDecision.action` 必须一致（3 组） | if/then 分别锁定 |
| P0-7 | `riskLevel` 必须等于 `risks[]` 中的最高等级 | 嵌套 if/then/else + contains |
| P0-8 | `trigger=always` → 阶段非 inMethod；`method:xxx` → 阶段必须 inMethod | if/then/else 锁定 phase |
| P0-9 | `decisionPoints[].id` 必须唯一（JSON Schema 无法表达数组唯一性） | validate 脚本新增 `_check_decision_point_uniqueness()` 业务校验 |
| P1-1 | `test_migrated_data_passes_v13_schema` 假阳性修复 | 先剥离 decisionPoints + 还原 schemaVersion=1.2 再走迁移路径 |
| P1-2 | 补充 16 个测试用例 | 新增 `TestConditionalConstraints`(13) + `TestBusinessValidation`(3) |
| P1-4/P1-5 | 示例数据 DP-comp comparison 虚构信息 + 语义矛盾 | 改为可溯源差异（小区名、面积差、修正指数） |
| P2-1 | 设计文档 `"comparison": null` 与 schema 冲突 | 删除，改"应省略字段" |

**技术要点（可复用经验，已记入工作日志）**：
1. **JSON Schema 同一对象只能有一组 `if/then/else`**，多组条件必须用 `allOf` 包裹
2. **description 里写的约束 ≠ 验证器执行**——凡语义约束必须用可执行规则（if/then/else 或业务校验）落地，并用测试锁定
3. **测试假阳性**：no-op 迁移测试测不到迁移路径，验证迁移必须先构造迁移前状态

设计文档命名为"报酬率确定"，示例数据命名为"资本化率确定"。示例使用 `directCapitalization` 模式所以"资本化率"技术上更准确，但两处文档应统一。

### 2.4 [P2-2] 驳回后的行为未在 schema 建模（未做）

### 2.5 [P2-3] evidenceItem.source 的 T0/T1/T2 等级非结构化（未做）

evidence 的 `source` 是自由文本，T0/T1/T2 等级嵌入在字符串中（如 "委托合同 (T0)"）。对比 `comparableInstances[].sourceGrade` 是结构化 enum。**建议**：在 `evidenceItem` 中加可选的 `sourceGrade` enum 字段。

### 2.6 [P2-4] calculationChain.version 仍为 "1.2"（未做）

示例数据 `schemaVersion: "1.3"` 但 `calculationChain.version: "1.2"`。这是设计意图（计算链格式版本独立于 schema 版本），但未在 CHANGELOG 或 schema description 中说明，容易引起困惑。

`rule` 可填任意文本、`passed` 可全 false 仍通过 schema。有意放宽——红线判定依赖线下专业核验，schema 只保证结构不代行业务判断。若需收紧：`rule` 改 enum + `passed=false` 时必填 `detail`。
